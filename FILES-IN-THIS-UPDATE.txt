SHORT ANSWER: YES, AND IT IS READY TO TEST TONIGHT
==================================================

One agent, two kinds of device, chosen by one line in agent.ini:

  Mode=reader      the Live20R / SLK20R on a PC's USB. Unchanged.
  Mode=terminal    the K50 on the network. New.

The Live20R path is untouched. Nothing about it changed.

To test with the K50 you have in your hand:

  1. Apply this bundle, restart the server.
  2. In HMS: Administration -> Attendance -> Devices -> Add a device, and
     pick "Terminal on the network". Copy the key it shows once.
  3. build.bat in the agent folder. No SDK, no driver, no DLL for terminal
     mode.
  4. In agent.ini:

       Mode=terminal
       DeviceIp=<the address under Menu > Comm > Ethernet on the K50>
       DevicePassword=0
       DeviceKey=<the key from step 2>

  5. CLOSE ZKBIO TIME. Some firmware allows only one connection at a time
     and this is the single most common reason a first attempt fails.
  6. Run:

       hms-attendance-agent.exe --probe

That last command is the one that matters. It connects, reads the clock,
counts what is on the device, lists everybody enrolled with who they map to
in HMS, and shows the last ten punches. It posts nothing and changes nothing
on the device. If it prints a table, the hard part works.


WHY THESE ARE NOT TWO KINDS OF THE SAME THING
=============================================

Worth reading once, because it decides everything else and it is the thing
people get wrong when wiring a K50 into a system built for a reader.

  A LIVE20R IS A PIECE OF GLASS ON A CABLE. It has no brain. HMS holds the
  fingerprints, the PC does the matching, and enrolment happens on the HMS
  screen because HMS is where the templates live.

  A K50 IS A COMPLETE COMPUTER ON THE WALL. People are enrolled ON IT, it
  matches them itself, and it keeps its own log. There is no useful way to
  push HMS templates into it and no reason to try: it already knows who
  everybody is.

So terminal mode does not identify anybody. It reads a log of decisions the
device has already made — a user id and a time — and forwards them. The one
thing it needs from HMS is which staff member a device user id belongs to.

Everything downstream is shared: the same queue, the same retry on a dropped
network, the same route into HMS, the same rows in the attendance table. You
can run a reader at one door and a terminal at another and no report will
know the difference.


MAPPING PEOPLE
==============

If the terminal is enrolled alongside HMS, give somebody user id 7 on the
device and HMS staff 7 gets the punch. NO MAPPING NEEDED.

Your K50 is the other case: it has been in service with ZKBio Time and has
its own numbering. So each person's device id goes against them in HMS:
Administration -> Staff -> Edit -> "Id on the attendance terminal". The
probe output is the list to work from — it prints every device user beside
either the HMS staff member they map to or "-- NOBODY --".

A punch from an id nobody claims is NEVER GUESSED INTO A STAFF MEMBER. It is
counted, named in the log, and dropped. A wrong guess files one person's
attendance under another's name, and nobody would ever find it.

Two people cannot be given the same device id. Without that the punches from
that id would land on whichever row the query returned first — silently, and
differently on different days.


WHAT IT WILL NOT DO
===================

IT NEVER CLEARS THE DEVICE LOG. The protocol has a command for it and this
agent does not send it. Clearing is the easy way to avoid reading a record
twice and it is the wrong way: the moment HMS is unreachable, or this PC is
off, or the mapping is wrong, the only copy of a day's attendance would be
gone. A high-water mark in last-punch.txt beside the exe does that job
instead, and it holds the timestamp plus the ids already sent at exactly
that second — because at shift change several people punch in the same
second, and a timestamp alone would either drop them or resend them forever.

IT DOES NOT PUSH FINGERPRINTS TO THE DEVICE. Enrol on the device.

ON A FIRST RUN IT IGNORES ANYTHING OLDER THAN FOURTEEN DAYS. Your K50 holds
months of ZKBio Time history and posting all of it would rewrite every
absentee report for those months. BackfillDays in agent.ini; 0 for a
deliberate back-fill.


THE DEVICE'S CLOCK IS THE ONE THAT MATTERS
==========================================

Every record a terminal hands over is stamped by ITS OWN clock, not the
server's. A device whose battery died and came back at midnight on the first
of January hands over a month of attendance dated in the year 2000, and HMS
stores it exactly as given, because there is no way to tell from the outside
that it is wrong.

The agent compares the two clocks on every poll and warns when they are more
than two minutes apart. To fix it:

  hms-attendance-agent.exe --probe --set-time

A record that decodes to an impossible date — which is what a blank or
corrupt slot does — is dropped rather than posted.


WRITTEN AGAINST THE PROTOCOL, NOT THE SDK
=========================================

ZKTeco ship zkemkeeper.dll for this and it would have been less code. It is
also a 32-bit COM component that an installer has to register, which pins
the agent to an x86 build and to a machine somebody has run a setup program
on. The whole point of this agent is that build.bat compiles it on an
offline hospital PC with nothing installed. So terminal mode speaks the
protocol over a socket: no SDK, no DLL, no driver, nothing to install.

HERE IS WHAT I COULD AND COULD NOT CHECK, PLAINLY.

I have no K50. The handshake with a real device is the one thing I could not
run, and I am not going to pretend otherwise.

What I DID do:

  - Took the wire format from the protocol documentation and from pyzk, the
    reference implementation most other ZKTeco integrations are built on,
    rather than from memory.
  - COMPILED the agent. I installed a C# compiler here and built it, so
    what you are getting is code that compiles rather than code that reads
    as though it would.
  - Wrote a test for the parts that are pure arithmetic and tested them
    against values produced by RUNNING the reference algorithm. 28 checks,
    all passing. You can run it yourself:

        test-protocol.bat

    It connects to nothing.

That test earned its place twice over:

  MY FIRST ATTEMPT ASSERTED THE WRONG CHECKSUM. I wrote 0xFC17 for the
  connect packet from memory. The code said 0xFC16 and the code was right:
  the reference folds the sum with minus 65535 rather than minus 65536,
  which is off by one from the ordinary ones-complement sum anybody would
  write from the description. A wrong checksum means the device ignores
  every packet in silence, so that one off-by-one would have been an evening
  with a packet sniffer.

  THE RECORD LAYOUT PUTS STATUS BEFORE THE TIMESTAMP and punch after it. I
  swapped them on purpose to see what happens: the test failed with
  "2039-05-03" instead of "2026-10-10 09:14:33". That is the dangerous kind
  of wrong — a date that looks like a date — and it would have survived a
  demo and surfaced weeks later as an attendance report nobody could
  explain.

What is still untested until you plug it in: the connect-and-authorise
handshake, the buffered-read flow on your particular firmware, and whether
your K50 uses the 40-byte record (it should) or an older one (the parser
handles 8, 16 and 40). --probe tells you all three in one command.


IF THE PROBE FAILS, IN THIS ORDER
=================================

  1. ping the device's address
  2. the device and the PC are on the same subnet
  3. Menu > Comm > Ethernet on the device shows that address
  4. ZKBIO TIME IS CLOSED. Most likely cause.
  5. DevicePassword matches Comm > Security > Comm Key (0 means none)

The agent prints that list itself when a probe fails, so it is there on the
screen rather than in a file.


ON THE HMS SIDE
===============

  Administration -> Attendance -> Devices is now "Attendance devices" with a
  Kind column, and adding one asks which it is. A terminal also takes its
  network address — documentation, so somebody can see which box on which
  wall a key belongs to. Nothing reads it to decide where to connect; the
  agent uses its own settings.

  Picking the kind changes nothing about how a punch is stored. It is there
  so nobody spends an afternoon trying to enrol a nurse from the HMS screen
  onto a box that was never going to listen. The form says so in words under
  the dropdown.

  Administration -> Staff -> Edit has "Id on the attendance terminal".

  A new route, /attendance/agent/roster, hands the agent the mapping. It is
  behind the device key like the other two agent routes, listed by exact
  path, and a terminal never fetches fingerprint templates it cannot use.

  Existing devices stay readers. An install that has never heard of a
  terminal behaves exactly as it did yesterday.
